# Подбор по требованиям к детали

> Прототип не готов к production: [результаты проверки и оставшееся решение](recommendation-status.md).

`POST /api/print-plans/analyze-stl` принимает STL, необязательный `description`
до 2000 символов и необязательные ручные настройки. Отсутствующее поле означает
автоматический подбор. Существующие HTTP-поля и формат результата сохранены.

## Как принимается решение

1. Локальная модель извлекает **независимые требования**: назначение, уровень и
   характер нагрузки, среду, гибкость, приоритет поверхности/посадки/скорости/экономии.
   Весь непустой текст проходит локальную модель. Каждый признак разбирается отдельным коротким вопросом; перехвата по ключевым словам больше нет. Шесть запросов выполняются последовательно в одном общем бюджете времени, без повторных попыток. Общий префикс содержит исходный текст и точные фрагменты для цитирования.
2. Каждое известное требование должно иметь короткую подтверждающую цитату из
   пользовательского описания. Схема генерации ограничивает цитаты фрагментами исходного текста. Все шесть
   признаков обязательны: известный код с цитатой или UNKNOWN с пустой строкой.
   Сервер дополнительно проверяет JSON, перечисления, поля, длины и наличие цитат в тексте. Нет подтверждения — ответ отклоняется целиком.
   UNKNOWN не превращается в придуманное условие. Цитирование защищает от выдуманного
   основания, но само по себе не доказывает правильность понимания отрицаний.
3. Справочник requirement-evidence.json отклоняет неподтверждённые выводы: гладкость
   не доказывает гибкость, будущее усилие не доказывает статический характер. Эти
   проверки не определяют профиль по ключевому слову и не обходят модель; они только
   заменяют сомнительный признак на UNKNOWN. Словарь ограничен русским и английским;
   редкая формулировка может остаться неопределённой. Код сочетает принятые требования
   и выбирает стартовые настройки из проверяемой политики.
   Нагрузка имеет приоритет над декоративным назначением, черновой печатью и экономией.
   Удары/вибрации увеличивают число стенок; поверхность/посадка уменьшают слой.
   Улица предлагает PETG, гибкость — TPU 95A. Нагрев требует проверки паспорта и условий.
4. Ручные настройки имеют приоритет. Если итоговый вариант ниже ориентира по
   заполнению/стенкам или материал противоречит условиям, результат объясняет расхождение.
5. До шести вариантов рассчитываются настоящим Bambu Studio для A1 mini 0,4 мм.
   Выбор по времени и расходу идёт только среди вариантов с заданными ограничениями.
   В рекомендациях используются фактические параметры выбранного кандидата.

Модель **не генерирует произвольные числа настроек** и не выдумывает физические
свойства. Это помощник по стартовым параметрам, а не механический расчёт STL.
Наличие разных описаний не обязано давать разные числа, если требования эквивалентны.

## Числа нагрузки и границы применения

Значения с Н/N, кН/kN, кг/kg сохраняются в пояснении в исходных единицах. Масса не
превращается молча в силу. 15 Н и 1500 Н сами по себе не дают оснований вычислить
процент заполнения: нужны направление усилия, опоры, плечо, ориентация слоёв,
материал и условия. Для численного требования предлагается рабочий базовый вариант
и явные вопросы; ни один профиль не называется способным выдержать указанную силу.
Для противоречивых и неполных условий результат остаётся предварительным.

HDT из паспорта — результат стандартного испытания, не допустимая рабочая температура
произвольной детали. Выбор PETG при нагреве не означает пригодность при 90 °C.
Точность посадки не гарантируется тонким слоем: нужны калибровка и проверка образца.
Геометрия влияет на слайсинг; анализ напряжений и автоматическая ориентация не выполняются.

## Основания политики

Это курируемые стартовые ориентиры, а не экспериментально подтверждённые нагрузки:

- [Prusa: заполнение](https://help.prusa3d.com/article/infill_42): обычные модели часто
  печатают с 10–15%; оболочка существенно влияет на прочность, заполнение — в том
  числе на поддержку верхних слоёв и сопротивление сжатию.
- [Prusa: рисунки заполнения](https://help.prusa3d.com/article/infill-patterns_177130):
  Gyroid — пространственный рисунок без пересечений в одном слое. Это не делает всю
  FDM-деталь изотропной и не доказывает её допустимую нагрузку.
- [Prusa: PLA](https://help.prusa3d.com/article/pla_2062),
  [PETG](https://help.prusa3d.com/article/petg_2059),
  [гибкие материалы](https://help.prusa3d.com/article/flexible-materials_2057):
  свойства и условия применения материалов; конкретные температуры берутся из
  существующего каталога паспортов, а не из ответа нейросети.

Ориентиры приложения: лёгкая нагрузка — 10%/2 стенки; рабочая деталь — 20%/3;
явная высокая нагрузка — 35%/4; удары/вибрация — не меньше 30%/5. Это проектные
эвристики для пробной печати. Они не являются формулой прочности из этих источников.
Экономия не снижает эти минимумы. Для поверхности/посадки предлагается слой 0,12 мм;
для быстрой печати без механических требований — 0,28 мм; иначе 0,20 мм.

## Защита сервера и отказ

Один слот охватывает разбор и слайсинг. Нет автоматических повторов и очереди из
пользовательских расчётов. Есть тайм-аут, лимит ответа 16 КБ, строгая проверка JSON.
Кеш описаний — 128 точных текстов на час; результат STL+запроса — 32 записи на 15 минут.
Ответы FALLBACK не кешируются ни на одном уровне: восстановившийся сервис можно
использовать при следующем явном расчёте. FALLBACK и неопределённые требования
показаны честно; они не выдаются за успешное понимание назначения.

Ollama получает только описание внутри приватной сети Compose; CAD не передаётся
модели. В логи не записываются текст, ответ модели и CAD. API-ключ и внешний AI-сервис
не требуются. Образ и веса первоначально скачиваются из официальных реестров.

## Проверка качества

Обычные тесты проверяют политику, приоритеты, ошибки транспорта и валидацию ответов.
Они **не подменяют оценку реального понимания текста**. Для неё есть отдельный набор
`src/test/resources/recommendation/requirements-cases.json`: пользовательская пара (не включена в примеры промпта),
отрицания, смешанные цели, улица, нагрев, гибкость, число без заданного характера
нагрузки, неопределённое описание и попытка дать модели инструкции.

```sh
python3 tools/evaluate-requirements.py --url http://PRIVATE_OLLAMA:11434 --model MODEL --output /tmp/requirements-results.json
```

Запуск последовательный, отправляет только публичные контрольные тексты и не вызывает
слайсер. Проверяет ожидаемые признаки и цитаты, печатает время и результат по каждому
примеру, завершается с ошибкой при расхождении. Набор небольшой; даже полный проход
не доказывает понимание любых описаний. Промпт и параметры декодирования совпадают
с приложением. Не запускается автоматически в CI без локальной модели.

`recommendation` по-прежнему содержит source (`LOCAL_MODEL`, `FALLBACK`, `DEFAULT`;
`RULES` сохранён только для старых клиентов), purpose, summary и items. В items
появились «Как поняли задачу», проверки конфликтов и вопросы по недостающим условиям. Основной текст показывает понятные признаки без технических цитат; основания доступны в диагностической записи тестов.
Существующий frontend отображает их без изменения контракта.

## Настройки и обновление инфраструктуры

- `PRINTLAB_RECOMMENDATIONS_ENABLED=true` включает разбор.
- `PRINTLAB_OLLAMA_URL=http://ollama:11434` — только внутренняя сеть.
- `PRINTLAB_REQUIREMENTS_MODEL=qwen2.5:7b-instruct-q3_K_M` — фиксированная версия Instruct,
  Q3_K_M, Apache-2.0, около 3,8 ГБ весов. Проверенный manifest ID: `29492a928341`.
- `PRINTLAB_REQUIREMENTS_TIMEOUT_SECONDS=90` включает запас на холодную загрузку;
  общий бюджет разбора и слайсинга остаётся 180 секунд. Нет повторной попытки в фоне.

Веса: [официальная модель](https://ollama.com/library/qwen2.5:7b-instruct-q3_K_M).
Формат: [Ollama Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs).
Внутренний ответ модели — шесть обязательных пар [код, цитата]. Для пар
используется JSON Schema prefixItems, для цитат — enum из исходных фрагментов;
при смене модели/версии сервера нужно заново прогнать семантический набор.

Ollama ограничена 3 CPU и 4352 МиБ, загружает одну модель и обрабатывает один запрос.
Шесть вопросов используют один загруженный runner; после разбора backend отдельно
просит выгрузить его до запуска слайсера. При ошибке выполняется та же очистка.
Две минуты keep_alive — запасной предел, если запрос очистки не дошёл. Кеш
требований позволяет не загружать модель повторно для того же описания.
Порт Ollama не публикуется, облачные функции отключены. Веса 1.7B можно сохранить
для отката; старый 1.7B-классификатор не подходит для нового формата требований.

Compose на VPS управляется отдельно от образа. До первого деплоя подготовьте
резервную копию `/etc/printlab/compose.yaml`, примените ресурсные настройки Ollama
и обновите модель/тайм-аут в окружении backend. Не заменяйте весь серверный файл:
в нём могут быть настройки других сервисов. Обновление backend подхватит значения
при следующем стандартном деплое. Существующие данные и bot-сервисы не изменяются.

```sh
docker compose --env-file /etc/printlab/compose.env -f /etc/printlab/compose.yaml exec -T ollama ollama pull qwen2.5:7b-instruct-q3_K_M
docker compose --env-file /etc/printlab/compose.env -f /etc/printlab/compose.yaml up -d --no-deps ollama
```

Не считайте PR готовым к выкладке без загрузки весов и полного теста на VPS:
обычные CI-тесты используют управляемые ответы и не измеряют качество нейросети.

Переменные PRINTLAB_OLLAMA_MODEL=Qwen3 1.7B и PRINTLAB_RECOMMENDATIONS_TIMEOUT_SECONDS=25
сохраняются для старого образа при откате. Новая версия предпочитает отдельные
PRINTLAB_REQUIREMENTS_MODEL и PRINTLAB_REQUIREMENTS_TIMEOUT_SECONDS. Старый backend
игнорирует новые переменные: увеличенный тайм-аут не ломает его проверку конфигурации.

Записанные реальные ответы отдельно проверяются через фактическую Java-политику:

```sh
./mvnw -Dtest=RecordedRecommendationEvaluationTest -Dprintlab.recommendation-evaluation=/tmp/requirements-results.json test
```

Набор фиксирует и ожидаемые признаки, и ожидаемые стартовые настройки. Различие
второстепенной метки может не менять итоговый профиль, поэтому эти две проверки
отчётливо разделены. Replay проверяет хеш промпта и вопросов; это не новые вызовы AI.
В обычном CI replay пропускается без указанной записи; сетевые тесты там используют
управляемые ответы. Сохраняются исходные ответы модели, а не только успешные случаи.
