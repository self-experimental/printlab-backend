# Первый публичный запуск: сайт, API, слайсер и Telegram

## Текущий статус

Приложение и Bambu Studio 02.08.02.61 проверены на macOS и Ubuntu 24.04.5 x86_64.
Первый сервер Hostkey запущен 25 октября 2026 года; его адрес, версии и команды
обслуживания описаны в [live-server.md](live-server.md). Файлы `deploy/` остаются
шаблонами: для нового сервера нужно установить Java, официальный Linux AppImage,
системные библиотеки и сертификат, заменить домен и проверить реальный расчёт.
Не переносите macOS-бинарник на Linux.

## Конфигурация первого сервера

- Москва не обязательна. Выбираем доступную локацию с хорошим соединением
  для пользователей и исходящим HTTPS к Telegram; архитектура x86_64,
  Ubuntu 24.04 LTS. Для первого запуска можно использовать Нидерланды.
- Для небольшого пилота: 4 vCPU, 8 ГБ RAM, от 80 ГБ SSD/NVMe, публичный IPv4.
- С запасом под расчёты и бот: 8 vCPU, 16 ГБ RAM, от 120 ГБ NVMe.
- Ежемесячная оплата на этапе проверки; ежедневные резервные копии вне VPS.
- SSH по ключу. Публичны только 80/443; SSH доступен администратору.
  Порт 8080 слушает только `127.0.0.1`.

Это исходная оценка ресурсов, а не обещание определённого числа пользователей.
Измеряем время и пиковую память на настоящих STL; сейчас допускается один
активный подбор на один процесс API. Размер сервера сам по себе не повышает
число параллельных расчётов.

## Размещение служб

```text
Браузер ── HTTPS ── Nginx ── /api/... ── Spring Boot ── Bambu Studio CLI
                     └──── статическая сборка фронта

Telegram ── исходящие HTTPS-запросы ── отдельная служба бота ── localhost API
```

Nginx раздаёт готовый `dist`, Vite на сервере не нужен. Java запускает
установленный рядом слайсер дочерним процессом: текущий API не умеет отправлять
задачи в отдельный контейнер со слайсером. Одна systemd-служба ограничивает
потребление Java и всех её дочерних процессов. При падении эта служба
перезапускается независимо от будущего бота и Nginx. При этом сбой или нехватка
памяти всего VPS затронет все службы; для первого пилота это допустимый компромисс.

Бот использует те же API и ограничения подбора. Он не читает и не изменяет JSON
напрямую, не запускает второй бэк и не обходит общий лимит слайсера.
Если позже понадобится очередь с отслеживанием статуса, добавляем её один раз
для сайта и бота. Сейчас занятость возвращается как `429 SLICER_BUSY`.

## Подготовка релиза

1. Установить Java 25 и официальный Linux Bambu Studio с системными профилями
   той же версии. Зафиксировать URL релиза и SHA-256 загруженного архива.
   Вначале проверить CLI под обычным пользователем без рабочего стола.
   При несовместимости Linux-бинарника или его зависимостей не открывать подбор.
   [Официальные релизы](https://github.com/bambulab/BambuStudio/releases),
   [документация CLI](https://github.com/bambulab/BambuStudio/wiki/Command-Line-Usage).
2. На машине сборки выполнить `./mvnw verify package` с Java 25.
   Фронт собрать с Node из `.nvmrc`: `npm ci`, `npm run check`.
   Сохранить Git SHA обоих репозиториев и версии Java/слайсера в описании релиза.
3. Разместить исполняемый JAR как `/opt/printlab/backend/releases/<release>/app.jar`,
   содержимое `dist` как `/var/www/printlab/releases/<release>/`.
   Ссылки `current` указывают на выбранные релизы. Файлы приложения принадлежат
   администратору; служба `printlab` может их читать, но не изменять.
4. Java доступна по `/opt/printlab/java/bin/java`, Linux-слайсер и профили — по
   путям в `deploy/backend.env.example`. Эти пути должны указывать на реальную
   установку с доступными зависимостями, а не на пустые каталоги.
5. Создать отдельного системного пользователя и группу `printlab` без входа в
   оболочку. Создать `/var/lib/printlab`, владелец `printlab:printlab`, права `0700`.
   До первого запуска положить туда `data/experiments.json` и
   `data/research-models.json` из репозитория, с теми же владельцем и правами `0600`.
   Существующие серверные данные при следующих релизах не перезаписывать.
   Локальные пользовательские STL из `data/uploads` не входят в релиз.
6. Скопировать `deploy/backend.env.example` в `/etc/printlab/backend.env`,
   задать реальные пути, владелец `root:root`, права `0600`.
   Установить `deploy/printlab-backend.service` в `/etc/systemd/system/`.
   Выполнить `systemd-analyze verify /etc/systemd/system/printlab-backend.service`,
   затем `systemctl daemon-reload` и `systemctl enable --now printlab-backend`.
7. Проверить локальный API и реальный подбор **под этой службой**, включая
   очистку временных файлов и завершение дочернего процесса по тайм-ауту.
   Лимиты шаблона: Java heap 1 ГБ; группа Java + слайсер до 5 ГБ памяти и
   300% CPU (эквивалент трёх ядер). Они оставляют запас на 8-ГБ VPS,
   но требуют замера на реальных моделях. При превышении памяти возможен
   перезапуск API и потеря текущего расчёта; это не очередь задач.
8. Привязать домен A-записью к IPv4. AAAA добавлять только после настройки IPv6
   на сервере и в Nginx. Получить сертификат HTTPS. Для первого выпуска можно
   временно поднять только HTTP-блок с `/.well-known/acme-challenge/`;
   пользовательские файлы на этом этапе не принимать.
9. Заменить `printlab.example.com` в `deploy/nginx.conf` настоящим доменом,
   проверить пути сертификатов и установить файл в `/etc/nginx/conf.d/`.
   Не оставлять одновременно старый конфиг с общим `location /api/` прокси.
   Выполнить `nginx -t`, затем перезагрузить Nginx. Проверить продление сертификата.
10. Открыть HTTPS-доступ и выполнить приёмку ниже. Включить наблюдение за
    доступностью сайта, API, перезапусками и свободным местом; ограничить размер
    journal/access/error логов. Nginx временно буферизует STL на диске; его каталог
    загрузок тоже учитывается при наблюдении за свободным местом.

## Какие маршруты открыты

Шаблон Nginx разрешает только используемые фронтом действия:

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET / HEAD | `/api/materials` | Каталог материалов |
| POST | `/api/print-plans/analyze-stl` | Подбор параметров со слайсером |
| POST | `/api/optimization/analyze-stl` | Сравнение с испытанными образцами |

Запись экспериментов, постоянная загрузка моделей, Swagger и остальные API
снаружи закрыты. Production-профиль также отключает Swagger и подробности
ошибок. Сам API не имеет полноценной авторизации: не выставляйте порт 8080
наружу и не добавляйте новые публичные маршруты без проверки доступа.

Два расчётных маршрута делят лимит Nginx 6 запросов/мин на IP, с коротким
допуском всплеска. Это начальная настройка пилота: общий IP офиса или мобильной
сети может принадлежать нескольким пользователям. Лимиты IP не заменяют защиту
от распределённой атаки; общий лимит одного слайсера, лимиты соединений,
размеров и ресурсов дополняют их. Автоматических повторов POST нет.
Если перед Nginx появится внешний прокси, отдельно настроить доверенные адреса
для определения IP; произвольным входящим `X-Forwarded-For` не доверять.

## Приёмка до приглашения пользователей

- Главная и вложенный маршрут открываются по HTTPS после перезагрузки.
- `GET /api/materials` возвращает каталог; неизвестный `/api/...` — 404.
- `POST /api/experiments` и `/api/models` недоступны извне.
- `GET /swagger-ui.html` и `/v3/api-docs` недоступны.
- Выбор/удаление STL в интерфейсе не вызывает расчёт или сохранение на сервере.
- Подбор `fixtures/stepped-block.stl` из фронтенда возвращает шесть вариантов
  с положительным временем и массой. После него временные STL/G-code удалены.
- Второй одновременный подбор другого STL возвращает понятное сообщение о
  занятости. Большие файлы и частые запросы не попадают в неограниченную очередь.
- После перезагрузки VPS сайт и API восстанавливаются; запрос к порту 8080
  из интернета не проходит. Проверены восстановление резервной копии и откат.

## Подключение будущего Telegram-бота

Кода бота в этих двух репозиториях сейчас нет; образ или команда запуска
появятся после выбора реализации. На старте подходит long polling
(`getUpdates`): нужен исходящий HTTPS к Telegram, отдельный входящий порт не нужен.
Проверить доступ к `api.telegram.org` именно с выбранного VPS до запуска.
Webhook и polling одновременно не используются. См.
[Telegram Bot API](https://core.telegram.org/bots/api#getupdates).

Бот запускается отдельным непривилегированным пользователем и отдельной
службой с автозапуском. Первоначальный ориентир памяти для простого бота —
256–512 МБ, фактический лимит зависит от кода. Токен хранится только на сервере
в закрытом файле окружения бота. Он не попадает в Git, фронт, сборку или логи.
У бота своё хранилище состояния; один polling-процесс на токен, сохранение
последнего обработанного обновления и защита от повторной обработки.

Если бот принимает модели, у него те же 15 МиБ, валидация и ограничения запросов.
Для расчёта он вызывает `http://127.0.0.1:8080/api/print-plans/analyze-stl`.
Поскольку localhost обходит Nginx, лимит частоты на пользователя бота нужно
реализовать в самом боте; общий лимит слайсера продолжает действовать на бэке.
Долгий polling нельзя блокировать ожиданием расчёта; обработка задач должна
иметь ограниченную конкуренцию. Перед запуском проверить совместную нагрузку
сайта и бота, а также поведение обоих клиентов при занятом слайсере.

## Обновления и откат

Хранить предыдущий релиз фронта и JAR. Перед обновлением делать резервную
копию `/var/lib/printlab`; сертификаты и закрытые настройки резервировать
отдельно, с ограничением доступа. Каталог материалов входит в JAR.
Не запускать два API на одних JSON-файлах. Остановить службу, переключить
`current`, запустить и проверить каталог + один реальный расчёт. При ошибке
вернуть прежнюю ссылку. Обновления слайсера и его профилей также требуют
повторного реального расчёта и перезапуска API, чтобы сбросить кеши.
